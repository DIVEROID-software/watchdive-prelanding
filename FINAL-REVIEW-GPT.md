## ON security/correctness review

The status token has a domain-separated HMAC, bounded shape and timing-safe comparison; fragment transport avoids server URL logs and third-party scripts are gated on token-bearing routes. Status/settings responses are explicitly allow-listed, settings do not accept arbitrary Notion properties, nicknames render as React text, and privacy/adversarial/token tests pass. Public progress reveals counts, not identities. Settings limits and shared read caching are per process, not distributed protection; full-scan cost remains on ON cache misses. CDN leaderboard staleness can delay visibility of an opt-out/hide and an OFF flip until existing cached responses expire; the handler's “next request” comment does not override CDN cache lifetime.

A low-probability consistency edge remains unmodified: `store.ts:149` picks the oldest-created row for a duplicate ref code, whereas the ledger and status cache choose lowest page ID. Code collisions therefore need fail-closed handling or a single ownership policy before relying on uniqueness as a security invariant. No real collision was observed or production data read. Pre-send claim counts may preserve tiers even if a crash/unknown outcome loses the notice; they are no longer proof a tier notice was delivered. Manual reward review and operational fulfillment remain necessary; this review does not certify reward delivery or legal compliance.
