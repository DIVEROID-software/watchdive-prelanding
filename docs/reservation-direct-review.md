# Direct reservation Checkout review — 2026-10-23

Branch: `feat/reserve-direct`, based on main `b176897`. This is a review candidate, not a production release.

The on-site offer can start the existing one-time USD 3 Checkout immediately after a clean pending signup. The server issues a domain-separated, row/email-bound HMAC credential lasting 15 minutes, rereads the exact current row before checkout, and uses only its canonical email and the fixed server price. A separate read-only 24-hour status scope lets a completed checkout return resolve after payment authority expires. Neither payment nor the webhook marks email verified. All nine card locales keep the USD 149 lowest-price promise, USD 200 next tier, separate-fee/refund/no-auto-charge/shipping-and-tax disclosures, terms link and secondary email-verification action.

The shared Stripe implementation keeps inbox/offer/attempt idempotency, reuses the winning open session, blocks already-paid/refunded/disputed states, and retires old open sessions without Checkout terms collection. New sessions require Stripe's terms checkbox and link `/terms` through custom text. The retrieved accepted-consent result is required for a modern paid snapshot; an existing completed charge with an invalid contract cannot authorize another charge. Pending session and PaymentIntent metadata carry the stable Notion page id; the webhook mirrors that email-matching page and compatible inbox rows. The mail scheduler already checks live paid state at selection and again immediately before delivery; an additional regression covers a customer who paid before verification and later becomes due.

New reservation emails enter a minimal CSP-nonced storage bridge at `/api/reservation/direct?lang=LOCALE&invite=SIGNED`, then its second GET validates the invite and 303-redirects to a fresh/reused Stripe-hosted Checkout URL. The bridge preserves existing sessionStorage return authorization/language and renders no second offer. Invalid, expired, already-paid, refunded, disputed, configuration and provider errors fall back to the existing `/reservation` states. HEAD never starts a session. Existing `/reservation#invite` entry points and terms form remain functional.
